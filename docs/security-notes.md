対象: AI記録支援(本番PoC) — `poc-app/`
最終更新: 2026-09-14

`CLAUDE.md`のセキュリティ方針の根拠・議論の到達点・宿題をここに残す。方針そのものは`CLAUDE.md`が正、本ファイルは「なぜそうしたか」の記録。

## 1. リスクの整理(2軸)

セキュリティの論点は2つに分かれる。混ぜると議論が空回りする。

### ① 正規のルートで、誰にデータが渡るか(法務・契約の話)

自由記述の本文(実名+健康情報を含みうる)が、正規の処理の中で外部3社に渡る:

| 渡り先 | 何が渡るか | 保存の有無 |
|---|---|---|
| Supabase(米国) | 記録本文(`source_text`)・6項目・施設/メンバー | 保存する |
| OpenAI(米国) | 記録本文(分類のため) | APIは既定で学習に使わない。不正監視で最大30日保持後に削除 |
| Vercel(米国) | `/api/structure`を通過する本文・セッションcookie | 保存しない(通過のみ)。ただしログ残留に注意 |

→ 解決手段は**契約・書類**(委託・越境移転・DPA確認)。

### ② 想定外の人に見られる経路(コード・運用の話)

事故になる確率の高い順:

1. **RLSポリシーの穴**(桁違いに最重要)。1本間違えれば、ログインした誰でも全施設の記録を読める。しかも第三者がサインアップして`authenticated`になれる状態だと、URLに到達できれば攻撃者は正規ユーザーになれる。
2. **アカウント乗っ取り**(パスワードのみ・MFAなし・現場でのタブレット共有)。
3. **ログへの本文残留**(`console.error`等)。
4. **ベンダー侵害**(コントロール外。委託先監督でカバー)。

→ 1が最重要なのは**唯一完全に自分の責任範囲**だから。SupabaseやOpenAIが破られる確率は下げられないが、RLSの穴は自分で作って自分で塞げる。

## 2. RLSがデータの唯一の境界線であることの実証

- Supabaseの`records`/`facilities`テーブルは、**アプリ(Vercel)を一切経由せず**、`https://<project>.supabase.co/rest/v1/records` として**インターネットに公開されている**。publishable keyはアプリのJSに埋め込まれ全訪問者に配られる(公開前提の設計)。
- 実測(2026-09-11): 未ログインで直叩き → `HTTP 401` / `code 42501 insufficient_privilege`。**RLSではなくGRANTで弾いている**(`schema.sql`が`authenticated`にしか権限を与えず`anon`に与えていないため)。
- プロジェクト作成時に **`Automatically expose new tables` のチェックを外した判断**がここで効いている。オンだと`anon`に自動付与され、RLS一枚だけが防御線になっていた可能性がある。
- 防御は2層: 未ログインの第三者はGRANT不在で弾かれる / サインアップした第三者は`authenticated`になりGRANTは通る→**ここから先はRLSだけ**。
- **境界線はVercelではない**。`サインアップ可否 + GRANT + RLS` の3つがデータの境界で、Vercel AuthenticationはUIを隠すだけ(Vercelを通らないので、Supabase直叩きは止められない)。

## 3. 越境移転(法28条)の整理

- クラウドに個人データを置くこと自体は**委託**で合法(CRMと同じ)。委託先は「第三者」に当たらず本人同意不要、代わりに委託元に監督義務(法25条)。
- ただし**委託先が海外だと越境移転(法28条)**が加わる。判断基準は**サーバーの物理的所在地ではなく「運営事業者が外国事業者か+データを取り扱えるか」**(出典: [PPC FAQ faq1-q12-3](https://www.ppc.go.jp/all_faq_index/faq1-q12-3/))。
- **Tokyoリージョンは越境を消さない**。SupabaseもOpenAIも米国事業者。Tokyoはレイテンシと外的環境把握には効くが、28条の適用そのものは消えない。
- **クラウド例外**(契約で「取り扱わない」+適切なアクセス制御なら「提供」に当たらず対象外)は、今回は怪しい。2026年3月にPPCが「保守用ID等で事業者が実際にアクセスできる場合は例外を使えない」と明確化しており、Supabase(マネージドPostgres)はこの形(出典: [牛島総合法律事務所](https://www.ushijima-law.gr.jp/client-alert_seminar/client-alert/20240329cloud/))。
- OpenAIはより明確に越境(リージョン選択肢なし・米国処理・本文を取り扱って出力生成)。

## 4. 無料プランでは順守確認の書類が取れない

委託先監督(法25条)は「証明」でなく「合理的な確認」を求めるが、その確認材料が有料プランの裏にある:

- **OpenAI**: API入力は既定で学習に使われない(訓練除外は設定可能)。ただし不正監視で最大30日保持。完全無保持(Zero Data Retention)は**Enterprise契約のみ**で、従量課金では使えない(出典: [OpenAI enterprise-privacy](https://openai.com/enterprise-privacy/))。
- **Supabase**: SOC 2 Type 2・ISO 27001・HIPAA対応・DPAあり。ただし**SOC 2レポートはTeam/Enterpriseでしか閲覧できず**、Freeでは取れない(出典: [Supabase SOC2](https://supabase.com/docs/guides/security/soc-2-compliance))。

→ 今の無料スタックでは「信用できるか」の前に「確認する書類が取れない」。残存リスク(ベンダーが嘘をつく/認証があっても侵害される)は消せず、全クラウドSaaS共通の値段。

## 5. 「本文が主戦場、名前マスタは副次」という気づき

- 職員が打つ本文「れんくんは検温36.8度、疲れ気味…」に実名+健康情報が既に入り、マスタの有無に関わらずOpenAI/Supabaseへ流れる。
- **マスタだけ仮名化しても本文が実名を漏らす**ので意味が薄い。逆にマスタを実名で持つ「追加の」プライバシー悪化もほぼ無い(本文が既に運んでいる)。
- 本当のレバーは「本文をこのクラウドに載せるか/載せるなら本文をマスクするか」。
- **この回の決定**: 仮名・ニックネーム運用で、実在児童を特定できる情報を**マスタにも本文にも入れない**。実在情報が無ければ移転される「個人データ」が無く、越境移転・DPAの論点が丸ごと消える。UI(`app/page.tsx`の入力欄上)に仮名入力の注意書きを表示して運用を実効化した。

## 6. 実データ移行時のゲート(先送りした条件)

仮名運用をやめて実在情報を扱う判断をするなら、その前に:

- (a) 有料プランに上げ、SupabaseのSOC2/DPA・OpenAIのZDRを取得
- (b) OpenAIへの送信前に個人名等をマスク、またはZDR適用
- (c) 越境移転の手当て(委託先の基準適合体制確認 + 相当措置or本人同意 + 外的環境把握)
- (d) 先方(事業所)の同意書・重要事項説明書に「記録を外部クラウドに保存する」旨の文言を追記
