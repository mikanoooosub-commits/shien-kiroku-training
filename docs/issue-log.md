# 障害票(バグ管理表)

対象: AI記録支援(本番PoC) — `poc-app/`
運用: 動作検証・実運用で見つかった不具合・挙動上の懸念をここに記録する。仕様・スキーマに影響する対応は`change-log.md`にも記載する。

## ISSUE-001: 事故・ヒヤリハット関連の記述が特記事項に反映されないことがある

| 項目 | 内容 |
|---|---|
| 発見日 | 2026-09-10 |
| 重大度 | 高(安全に関わる情報の見落としに直結するため) |
| 状態 | 対応済み(恒久解決ではなく緩和策。下記「残課題」参照) |

**事象**

実際に`gpt-4o-mini`を呼び出して検証した際、「おやつの後にたっくんと少しぶつかってヒヤリハットになりかけましたが、すぐ間に入って落ち着きました。」という、明示的に「ヒヤリハット」という語を含む文が、`incident`(特記事項)ではなく`activity`(活動内容)に混入した。結果、`incident`は空文字となり画面上は「該当なし」ときれいに表示された。`uncertainNotes`にも計上されず、AIはこの分類に自信を持っていた(=AI自身の自己申告の仕組みでは検知できなかった)。

**原因**

LLMによる分類は確率的であり、システムプロンプトの指示だけでは特定カテゴリへの計上を保証できない。加えて、UI設計上「該当なし」という表示が「本当に該当する記述がない」場合と「AIが見落とした」場合を区別できなかった。

**対応**

1. システムプロンプト(`app/api/structure/route.ts`)に「安全に関わる語を含む文は、他項目と内容が重複してでも必ず`incident`にも含めること」を明記。→ CHANGE-003
2. 原文中の安全関連キーワード(ヒヤリハット・事故・転倒・ぶつか等)をクライアント側(`app/page.tsx`の`findIncidentMismatches`)で独立に検出し、`incident`にも`uncertainNotes`にも反映されていない場合は機械チェックの警告(`.mismatchCallout`)を表示する安全網を追加。→ CHANGE-004

**再検証結果(2026-09-10)**

- 元の失敗事例(れんくんサンプル)は対応1により解消し、`incident`に正しく分類された。
- 一方、対応1の適用後に**別のサンプル文(みおちゃんサンプル)で同種の見落としが新たに発生**した(「特にトラブルやヒヤリハットはありませんでした。」が`incident`に計上されず「該当なし」表示に)。このケースでは対応2の機械チェックが正しく警告を表示し、見落としを検知可能にする設計が意図通り機能することを確認した。

**残課題**

- プロンプト改善はLLMの確率的な見落としを減らすだけで根絶はしない。これは想定通りであり、README「この先の設計方針」(AIは間違える前提で、直す手間を小さくする)と整合する。
- 機械チェック(対応2)は`incident`カテゴリのみに限定して実装している(実例が1件のみの段階で6項目全部に汎用化するのは時期尚早と判断)。他項目(引き継ぎ等)で同種の見落としが繰り返し観測されたら、対象カテゴリを広げることを検討する(ISSUE-002参照)。

## ISSUE-002: 引き継ぎ事項が連絡事項に混入し「該当なし」になることがある

| 項目 | 内容 |
|---|---|
| 発見日 | 2026-09-10 |
| 重大度 | 低〜中(安全情報ではなく事務連絡の遅延リスク) |
| 状態 | 対応済み(2026-09-10) |

**事象**

ISSUE-001の対応後の再検証中(れんくんサンプル)、「次の担当の田中さんに、れんくんが今日少し疲れ気味だったことを申し送りしておいてください。」という引き継ぎ内容が`handover`ではなく`contact`(連絡事項)にまとめて計上され、`handover`が「該当なし」になった。Supabase接続後の通し検証でも再現した。

**原因**

`contact`と`handover`の定義が「連絡・お願い」対「引き継ぎ・申し送り」という**内容ベース**の区別になっていた。しかし問題の2文はどちらも「〜してください」という依頼形で、モデルが**隣接する依頼文をまとめて同じ項目に入れて**いた。内容の種類では区別がつきにくい書き方だった。

**対応**

区別の軸を**宛先ベース**に変更した。→ CHANGE-008

- `app/record.ts`: `contact`を「【宛先が保護者・家族】」、`handover`を「【宛先が施設内の他の職員】」と明示(この説明文はJSON Schemaに載り、項目ごとの指示としてモデルに渡る)。
- `app/api/structure/route.ts`: システムプロンプトに「形ではなく宛先で判断する」「依頼形の文が続いていても、まとめて同じ項目に入れず文ごとに宛先を見る」を追加。

**再検証結果(2026-09-10)**

同一入力で複数回実行し、両方向の誤りが出ないことを確認した(LLMの分類は実行ごとにブレるため、1回の成功では確認にならない)。

| 入力 | 実行回数 | 結果 |
|---|---|---|
| れんくんサンプル(職員向け申し送りを含む) | 3回 | 3回とも`handover`に正しく分類。`contact`への混入なし。`incident`のヒヤリハット分類にもリグレッションなし |
| みおちゃんサンプル(保護者向けと職員向けを両方含む) | 3回 | 3回とも保護者向け→`contact`、職員向け→`handover`に正しく分類 |

**残課題**

6回の試行で誤りが出なかったというだけであり、確率的な誤分類が根絶されたことの証明にはならない(ISSUE-001と同じ性質)。実運用で再発した場合は、`incident`と同様の機械チェックの追加を検討する。

## ISSUE-003: 施設を作成できない(`new row violates row-level security policy for table "facilities"`)

| 項目 | 内容 |
|---|---|
| 発見日 | 2026-09-10 |
| 重大度 | 高(施設が作れず、アプリが一切使い始められない) |
| 状態 | 対応済み |

**事象**

Supabase接続後の初回通し検証で、サインアップ直後の「施設を作成する」が必ず失敗した。エラーは `new row violates row-level security policy for table "facilities"`。

**原因(切り分けの経過つき)**

当初は「`schema.sql`が途中までしか適用されず、INSERTポリシーが作られていない」と推測したが、`pg_policies`等を確認したところスキーマは完全に適用されており、`facilities: authenticated can insert`(`with check (true)`)も存在していた。セッションのJWTクレームも `role: authenticated` で正常だった。

真因は**`RETURNING`とAFTER INSERTトリガーの実行順序**だった。クライアントは `insert({name}).select("id, name")` としており、これはSQLでは `INSERT ... RETURNING` になる。PostgreSQLは`RETURNING`で行を返す際にSELECTポリシー(`using (is_facility_member(id))`)で可視性を判定するが、作成者をメンバーに登録する`handle_new_facility`は**AFTER INSERTトリガー**なので文の終わりに発火する。したがって`RETURNING`の評価時点では作成者はまだメンバーではなく、「自分が今作った行が見えない」と判定されて失敗していた。

INSERT自体は成功しているのにINSERTのポリシー違反に見えるエラーが出るため、原因を取り違えやすい。

**対応**

`app/facility.ts` の `createFacility()` から `.select()` を外し(=`RETURNING`を要求しない)、作成後に改めて `getMyFacility()` で取り直す形にした。トリガー側は「施設作成者は必ずメンバーになる」というDBレベルの不変条件として正しいので変更していない。→ CHANGE-007

**再検証結果(2026-09-10)**

修正後、サインアップ → 施設作成 → AI生成 → 保存 → リロード後の復元 → 別ユーザーからの不可視(RLS) → 招待 → 招待先での共有表示、まで通しで成功した。

## ISSUE-004: 1文に複数項目の情報が混ざっていると、片方の項目が空欄になる(観察のみ・未対応)

| 項目 | 内容 |
|---|---|
| 発見日 | 2026-09-10(本番デプロイ後の通し確認中) |
| 重大度 | 低〜中(記載漏れに見えるが、安全情報ではない) |
| 状態 | 未対応(観察記録のみ) |

**事象**

本番環境で新規のダミー文「ゆうくんは10時に登所して検温は36.5度、体調は良好でした。」を投入したところ、この1文がまるごと`attendance`(出欠・入退室)に分類され、`health`(健康面)が空欄になった。検温結果と体調は本来`health`に記載されるべき情報で、支援記録の必須項目でもある。

**原因**

モデルが**文単位で項目に割り当てている**ため。1つの文に「登所した」(出欠)と「検温36.5度・体調良好」(健康面)という別項目の情報が同居していると、どちらか一方の項目にしか計上されない。ISSUE-001・002が「どの項目に入れるかの判断ミス」だったのに対し、これは「1文を分割して複数項目に配れていない」という別の性質の限界。

**判断**

現時点では未対応とする。理由:

- 安全情報ではないため、ISSUE-001のような機械チェックを追加する優先度は高くない。
- 「文を分割して複数項目に配る」ようプロンプトで指示すると、逆に文脈が切れた不自然な下書きが増える恐れがあり、副作用の検証コストが大きい。
- 現場の使い方としては、職員が空欄に気づいて検温結果を書き足す形で吸収できる(「直す前提で作る」という設計方針の範囲内)。

**対応**

なし(観察を継続する)。実運用で「必須項目が空欄のまま提出される」事例が出たら、必須項目の空欄警告(特記事項の機械チェックと同様の仕組み)を検討する。

## ISSUE-005: 「直近記録を踏まえた一言」がほとんど発火せず、発火しても内部メッセージが記録に漏れることがある

| 項目 | 内容 |
|---|---|
| 発見日 | 2026-09-16 |
| 重大度 | 中(機能が実質使えない。安全情報の見落としではない) |
| 状態 | 対応済み |

**事象**

CHANGE-010で追加した「同じ児童の直近の記録(健康面)を参考情報としてAIに渡し、`health`に関連があれば書き足す」機能について、ユーザーが実際にたろう君の3日分のダミーデータ(体調良い→体調悪い→体調直ってる)で試したところ、再生成しても前回への言及が出ないと報告があった。

調査のため、本番の`/api/structure`と同一のプロンプト・スキーマをコピーした検証スクリプトで、明確に関連が読み取れるはずの入力(前回「発熱37.6度、給食を残した」→今回「検温36.5度、給食完食」)を`gpt-4o-mini`で4回試したところ、3回は`health`に何も書き足されず、書き足された1回も内部の参考情報メッセージの接頭辞文字列(「【参考情報・直近の記録(健康面)/本文ではない】」)がそのまま記録本文に漏れ出ていた。

**原因**

CHANGE-010時点の実装は、6項目への分類という主タスクの1回の呼び出し・1個のプロンプトの中に、「条件を満たせば`health`の末尾に一言書き足す」という副次タスクを埋め込んでいた。指示の分量・優先度の面で主タスクに埋もれ、副次タスクがほとんど実行されなかった。ISSUE-001(ヒヤリハットの見落とし)と同じ「指示だけでは確率的に見落とす/混ざる」性質だが、今回はカテゴリの取り違えではなく機能そのものの不発火という形で現れた。

**対応**

直近記録との比較・一言の生成を、6項目分類とは別の専用の小さい`responses.parse`呼び出し(`ContinuityNoteSchema`、`health`欄だけを見る)に分離した。`health`の`.describe()`とシステムプロンプトからは比較関連の指示を削除し、分類呼び出しは元の6項目分類のみに専念させた。→ CHANGE-012

**再検証結果(2026-09-16)**

同一の検証スクリプトで同条件を4回試したところ、4回とも狙った一言(「前回は〜、今回は〜」の事実の並び)が付き、断定的な評価語(悪化した/改善した等)も内部メッセージの漏れも再現しなかった。あわせて、今回と参考情報のどちらかが空・話題が無関係な場合に空文字を返すかも別途確認し、概ね意図通りだった(無関係な話題の組み合わせでも稀に一言が付くことがあったが、事実に基づく記述であり創作・改ざんには当たらないため許容範囲と判断)。

**残課題**

- 「話題が無関係なら空文字にする」判定は完全ではない(上記の稀な例外)。実運用で気になる事例が出たら、判定基準をより具体的にすることを検討する。
- 6回程度の試行での確認であり、ISSUE-001・002と同様に確率的な問題の根絶を証明するものではない。
